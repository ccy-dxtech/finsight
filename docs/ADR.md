# Architecture Decision Records

## 철학
- MVP 속도를 최우선으로 한다. 같은 문제는 한 가지 단순한 방법으로 풀고, 처리하지 않는 경우는 `docs/PRD.md`의 "한계"에 남긴다.
- 타협하지 않는 것은 네 가지다: **데이터 격리**(RLS), **결제 상태 정확성**(웹훅이 단일 출처), **금액 정확성**(숫자는 코드가 계산), **비밀값 보호**(서버 전용).

---

### ADR-001: Next.js App Router + TypeScript + Tailwind, Vercel 배포
**결정**: Next.js App Router(TypeScript strict)로 랜딩·대시보드·API를 한 앱에 만들고 Vercel에 배포한다.
**이유**: 화면과 서버 API(라우트 핸들러)를 한 저장소에서 다룰 수 있다. Polar와 Supabase 모두 Next.js 연동 가이드가 있다.
**트레이드오프**: 분석 요청이 Vercel 함수 실행 시간 한도에 묶인다(ADR-008).

### ADR-002: Supabase (Google 로그인 + Postgres RLS)
**결정**: 인증은 Supabase Auth의 Google OAuth 하나만 쓴다. 데이터는 Supabase Postgres에 두고 모든 사용자 테이블에 RLS를 건다.
**이유**: 비밀번호 관리와 이메일 발송이 필요 없다. 데이터 격리를 DB 정책으로 보장한다.
**트레이드오프**: Google 계정이 없는 사용자는 가입할 수 없다. 카카오 로그인은 없다.

### ADR-003: Polar sandbox 구독 결제
**결정**:
- Polar(판매 대행 MoR)로 Pro 월 구독 상품 하나(월 1,000원)를 판다. `@polar-sh/nextjs` 어댑터로 checkout·고객 포털·웹훅을 처리한다.
- 해지·카드 변경은 Polar 고객 포털에 맡긴다.
- MVP는 sandbox만 쓴다.
**이유**: 국내 PG 계약이나 사업자등록 없이 구독 결제를 붙일 수 있다. 원화 가격을 지원한다(조직 기본 통화 가격도 함께 설정해야 함). 해지 UI를 직접 만들 필요가 없다.
**트레이드오프**: 결제 화면이 Polar 디자인이다. sandbox에서 정기 갱신이 실제로 도는지는 확인하지 못했다.

### ADR-004: 플랜 상태는 웹훅으로만 갱신
**결정**:
- `subscription.active`가 오면 `pro`, `subscription.revoked`가 오면 `free`로 바꾼다. `subscription.canceled`는 무시한다(기간 끝까지 Pro).
- `profiles.plan`은 웹훅(service role)만 쓸 수 있다.
- 웹훅 기록 테이블과 결제 상태 폴링은 두지 않는다.
**이유**: 결제 상태의 단일 출처를 하나로 유지한다. 리다이렉트 파라미터는 위조할 수 있다.
**트레이드오프**: 결제 직후 웹훅 도착 전까지 Free로 보인다("결제 확인 중" 안내). 웹훅 순서 역전과 중복은 처리하지 않는다.

### ADR-005: 역할별 모델 분리 (Haiku 5.5 / Opus 5.5)
**결정**:
- 열 매핑과 가맹점 분류는 `claude-haiku-5-5`(effort low)가 맡는다.
- 인사이트 리포트는 Free와 Pro 모두 `claude-opus-5-5`(effort medium 명시)가 쓴다.
- 모델 ID는 `CLAUDE_MODEL_FAST`와 `CLAUDE_MODEL_SMART` 환경 변수로 주입한다.
**이유**: 반복적이고 양이 많은 일은 싸고 빠른 모델에, 해석과 조언은 가장 좋은 모델에 맡긴다. 등급 차이는 리포트 품질이 아니라 기능과 횟수로 둔다.
**트레이드오프**: 두 모델의 프롬프트를 각각 관리해야 한다.

### ADR-006: 구조화 출력 + "숫자는 코드, 해석은 AI"
**결정**:
- 모든 AI 호출은 구조화 출력(`output_config.format` + zod 스키마)으로 JSON을 받고 zod로 다시 검증한다.
- AI 출력 스키마에는 금액 필드를 두지 않는다. 거래는 id로 참조한다.
- 합계·건수·증감률은 `lib/aggregate`가 계산한다.
**이유**: 금액 정확성 때문이다. AI가 만든 숫자를 화면에 보여주지 않는다. 파싱 실패도 줄어든다.
**트레이드오프**: 리포트 문장 안의 표현은 자유도가 줄어든다. 프롬프트에 "금액을 계산해 쓰지 말라"는 지시를 넣어야 한다.

### ADR-007: 원본 미저장, 정리된 거래만 저장, 매핑 입력 마스킹
**결정**:
- 업로드 파일은 메모리에서 처리하고 버린다. 날짜·가맹점·금액·카테고리만 저장한다.
- 열 매핑에는 상단 10행만 보낸다. 그 전에 6자리 이상 연속된 숫자는 마스킹한다.
**이유**: 민감한 금융 데이터를 최소한으로만 다룬다. 월별 추이 비교를 위해 거래 저장은 필요하다.
**트레이드오프**: 같은 파일로 재분석하려면 다시 업로드해야 한다. 상단 행의 이름 같은 텍스트는 AI에 갈 수 있다(한계로 문서화).

### ADR-008: 단일 분석 요청 + NDJSON 진행 스트림 + 마지막에 한 번에 커밋
**결정**:
- `POST /api/analyze` 하나가 파싱부터 저장까지 처리한다. 진행 단계는 NDJSON 스트림으로 보낸다.
- 저장과 차감은 마지막에 `commit_analysis` RPC 하나로 처리한다.
**이유**: 중간 상태가 DB에 남지 않는다. 실패하면 깨끗하게 재시도할 수 있고 차감도 없다. 작업 큐와 상태 테이블이 필요 없다.
**트레이드오프**: 분석 중에 화면을 떠나면 취소될 수 있다. 전체 처리 시간이 Vercel `maxDuration` 안에 들어와야 한다.

### ADR-009: 사용량은 별도 `usage` 테이블 + RPC에서 확인·차감
**결정**:
- 월별 사용 횟수는 `usage(user_id, month, count)`에 둔다.
- 한도 확인과 +1은 security definer RPC 안에서 리포트 저장과 같은 트랜잭션으로 처리한다. 리포트 생성에 성공했을 때만 차감한다.
**이유**: 사용자가 횟수를 조작할 수 없게 한다. 동시 요청으로 한도를 넘기는 것을 막는다. "데이터 전체 삭제"로 횟수가 초기화되지 않는다.
**트레이드오프**: 테이블과 RPC가 하나씩 늘어난다.

### ADR-010: SheetJS 하나로 CSV·xls·xlsx 파싱
**결정**:
- 세 형식 모두 SheetJS로 읽는다. SheetJS는 npm 레지스트리 버전이 오래돼서 공식 배포처(cdn.sheetjs.com)의 패키지를 설치한다.
- CSV는 UTF-8(fatal)로 먼저 읽고, 실패하면 EUC-KR(`TextDecoder`)로 읽은 뒤 SheetJS로 파싱한다.
**이유**: 국내 카드사는 엑셀(구형 xls 포함)과 EUC-KR CSV를 많이 쓴다. 라이브러리 하나로 모든 형식을 처리한다.
**트레이드오프**: 암호가 걸린 엑셀은 지원하지 않는다.

### ADR-011: 중복 거래 키 = (날짜, 가맹점, 금액)
**결정**: 이전 업로드에 같은 키가 있는 거래는 저장하지 않는다. 같은 파일 안의 겹치는 거래는 모두 저장한다.
**이유**: 같은 파일을 다시 올리거나 기간이 겹치는 파일을 올려도 월별 추이가 중복 집계되지 않는다. 업로드 단위 삭제 기능이 필요 없다.
**트레이드오프**: 다른 파일에 나뉘어 있는 진짜 동일 거래는 하나로 합쳐진다.

### ADR-012: 고정 카테고리 10개
**결정**: 식비 / 카페·간식 / 교통 / 쇼핑 / 구독·정기결제 / 주거·통신 / 의료·건강 / 문화·여가 / 교육 / 기타. 목록은 `lib/categories.ts` 한 곳에서 정의한다. 사용자는 수정할 수 없다.
**이유**: 달마다 같은 기준이어야 추이를 비교할 수 있다. AI 출력은 enum으로 제한한다.
**트레이드오프**: 분류가 틀려도 사용자가 고칠 수 없다.

### ADR-013: 차트는 외부 라이브러리 없이 HTML/CSS 막대
**결정**: 카테고리 가로 막대와 월별 세로 막대를 Tailwind로 직접 그린다. 카테고리별 증감은 차트 대신 표로 보여준다.
**이유**: 필요한 차트가 단일 색 막대 두 종류뿐이다. 의존성과 번들 크기를 줄인다.
**트레이드오프**: 복잡한 차트가 필요해지면 라이브러리를 다시 검토해야 한다.

### ADR-014: Vitest + TDD
**결정**: 테스트는 Vitest로 하고, 대상 파일 옆에 `*.test.ts`로 둔다. `lib/`의 순수 함수(파싱, 정규화, 중복, 집계, KST 월 경계)를 중점적으로 테스트한다.
**이유**: CLAUDE.md의 TDD 규칙과 `tdd-guard` 훅이 테스트 파일을 요구한다. 금액·날짜 로직은 테스트로 지켜야 한다.
**트레이드오프**: 외부 API(Claude, Polar, Supabase)는 모킹해서 테스트하므로, 실제 연동은 수동으로 확인해야 한다.
