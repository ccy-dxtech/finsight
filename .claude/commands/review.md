이 프로젝트의 변경 사항을 리뷰하라.

리뷰 대상: $ARGUMENTS
(비어 있으면 지금 브랜치. git 범위(`main...HEAD` 등)나 PR 번호를 받을 수 있다.)

정확성·보안·아키텍처(화면이 바뀌면 사용자 여정까지)는 `review-code` 워크플로가 차원별 리뷰어를 병렬로 돌려 맡고, 나머지 항목은 네가 직접 확인한 뒤 결과를 하나로 모은다.

## 1. 범위와 출력 대상 정하기

1. `gh pr view --json number,url,baseRefName,headRefOid`로 PR을 찾는다(PR 번호를 받았으면 `gh pr view <번호> ...`).
   - PR이 있고 `git rev-parse HEAD`가 `headRefOid`와 같으면: 범위는 `origin/<baseRefName>...HEAD`(먼저 `git fetch origin <baseRefName>`), 출력은 **PR**이다.
   - 그 밖의 경우는 출력이 **콘솔**이다. gh 로그인 안 됨, PR 없음, 푸시하지 않은 커밋이 있음, 다른 브랜치의 PR 번호가 여기에 들어간다. 왜 콘솔인지 한 줄로 알린다(예: "PR이 없어 콘솔에 출력해요", "푸시하지 않은 커밋이 있어 콘솔에 출력해요. 푸시 후 다시 실행하면 PR에 코멘트를 남겨요").
2. 콘솔 출력일 때 범위는 `$ARGUMENTS`의 git 범위 → `main...HEAD` 순서로 정한다. 그 diff가 비면 커밋하지 않은 변경(`git diff HEAD`와 `git status --short`의 새 파일)을 리뷰한다.
3. `git diff --name-only <범위>`(작업 트리면 새 파일 포함)로 바뀐 파일을 나눈다.
   - 코드 파일: `src/**`, `supabase/**`, `package.json`, `*.config.*`, `scripts/**`
   - 화면 파일: `src/app/**`, `src/components/**`, `globals.css`

## 2. 리뷰어 병렬 실행 (Workflow)

코드 파일이 하나라도 있으면 Workflow 도구로 저장된 워크플로를 부른다.

```
Workflow({ name: "review-code", args: { range: "<범위>", files: [<바뀐 코드 파일>], screenFiles: [<바뀐 화면 파일>] } })
```

- 워크플로는 `correctness-reviewer`·`security-reviewer`·`architecture-reviewer`(화면 파일이 있으면 `ux-reviewer`까지)를 병렬로 돌리고, 차원마다 검증 에이전트가 지적을 반박 검증한 결과를 돌려준다.
- 이름으로 부르는 워크플로와 에이전트 정의는 세션을 시작할 때 읽힌다. 이름을 못 찾거나 이번 세션에서 스크립트를 고쳤으면 `name` 대신 `scriptPath: "<저장소 절대경로>/.claude/workflows/review-code.js"`로 부른다. 에이전트 정의가 아직 등록되지 않았으면 워크플로가 기본 에이전트에게 정의 파일을 읽혀 대신 돌린다.
- 문서만 바뀌었으면 부르지 않고 해당 행을 "해당 없음"으로 적는다.
- Workflow 도구를 쓸 수 없으면(Codex, 하네스 step 등) `.claude/agents/<이름>-reviewer.md`를 차례로 읽고 그 지시대로 직접 확인한다.

## 3. 워크플로가 도는 동안 직접 확인

워크플로는 백그라운드로 돈다. 기다리지 말고 아래를 확인한다.

- 문서 읽기: `/AGENTS.md`, `/docs/ARCHITECTURE.md`, `/docs/ADR.md`. 화면 파일이 바뀌었으면 `/docs/UI_GUIDE.md`, `/docs/UX_GUIDE.md`, `/docs/design-system/README.md`도 읽는다
- 체크리스트 3·4(TDD 순서)·7·8·10번 (아래 표의 "담당: 메인")
- 빌드 가능: `npm run lint`, `npm run test`, `npm run build`

## 4. 취합

- 리뷰어 지적은 그대로 옮기지 않는다. `confirmed`도 `파일:줄`을 직접 열어 한 번 더 보고, `uncertain`은 코드로 확인해 넣거나 "확인 못 함"으로 옮긴다.
- 같은 원인을 여러 리뷰어가 지적했으면 하나로 합치고, 가장 가까운 체크리스트 행에 넣는다.
- 심각도는 아래 공통 기준으로 다시 맞춘다. 리뷰어는 자기 차원을 중요하게 보고 심각도를 올리는 경향이 있다.
  - **P0**: 출시를 막음. 다른 사용자 데이터 접근, 비밀값 노출, 결제 없이 Pro, 금액·합계가 틀리게 표시됨, 사용자 데이터 손실, 사용자 단계가 끊김
  - **P1**: 고쳐야 함. 특정 입력·상태에서 틀린 동작, 규칙 위반이지만 바로 피해가 나지 않음
  - **P2**: 다듬기
- 외부 SDK(Polar, Supabase, Anthropic)의 필드나 동작에 대한 지적은 `node_modules`의 실제 타입·코드로 확인한 뒤에만 적는다. 예: Polar `/2026-10` 웹훅 payload는 `product_id`, `customer.external_id`처럼 snake_case다.
- `preExisting: true` 지적은 "기존 문제"로 따로 모으고 심각도 집계에 넣지 않는다. 반박되어 빠진 지적(`refuted`)은 건수만 적는다.

|---|---|---|---|
| 1 | 아키텍처 준수 | ARCHITECTURE.md의 디렉토리 구조·레이어·패턴, 단일 출처를 따르는가? | architecture |
| 2 | 기술 스택 준수 | ADR에 정의된 기술 선택을 벗어나지 않았는가? | architecture |

## 5. 출력

맨 위에 머리줄을 둔다.

```
범위: <범위> · 리뷰어: correctness ✅ security ✅ architecture ✅ ux 해당 없음 · P0 n건 · P1 n건 · P2 n건 · 반박되어 뺀 지적 n건
```

리뷰어가 돌지 못했으면 ✅ 대신 "실패"를 적고, 그 차원을 직접 확인했는지 밝힌다.

### 콘솔 (PR이 없을 때)

머리줄 다음에 표와 지적을 적는다.

| 항목 | 결과 | 비고 |
|------|------|------|
| 아키텍처 준수 | ✅/❌ | {상세} |
| 기술 스택 준수 | ✅/❌ | {상세} |
| 테스트 존재 | ✅/❌ | {상세} |
| CRITICAL 규칙 | ✅/❌ | {상세} |
| 정확성 | ✅/❌/해당 없음 | {상세} |
| 보안 | ✅/❌/해당 없음 | {상세} |
| 빌드 가능 | ✅/❌ | {상세} |
| 화면 규칙 | ✅/❌/해당 없음 | {상세} |
| 사용자 여정 | ✅/❌/해당 없음 | {상세} |
| 문서·E2E 동기화 | ✅/❌ | {상세} |

표 아래에 지적을 심각도 순으로 적는다. 지적마다 `[P0|P1|P2] 한 줄 요약`, `파일:줄`, 실패하는 상황, 근거, 수정 방안을 쓴다. 마지막에 "기존 문제"와 "확인 못 함"을 따로 모은다.

### PR (PR이 있을 때)

PR 리뷰 하나로 올린다. 승인이나 변경 요청은 하지 않고 코멘트로만 남긴다.

1. 지적마다 인라인으로 달 수 있는지 본다. `git diff -U3 <범위> -- <파일>`의 hunk 머리(`@@ -a,b +c,d @@`)에서 새 쪽 범위 `c`~`c+d-1` 안에 `line`이 있으면 인라인, 아니면(줄 0 포함) 본문으로 보낸다.
2. 인라인 코멘트 본문은 아래 모양이다.

   ````
   **[P1] 한 줄 요약** · 보안
   실패 상황: ...
   근거: ...
   → 수정:
   ```ts
   붙여 넣을 수 있는 코드
   ```
   ````

3. 리뷰 본문(`body`)에는 머리줄 + 위 10행 표 + 인라인으로 못 단 지적 + 기존 문제 + 확인 못 함을 넣는다.
4. payload를 임시 파일(스크래치패드나 `mktemp`)에 UTF-8 JSON으로 쓰고 올린다.

   ```json
   { "commit_id": "<headRefOid>", "event": "COMMENT", "body": "<본문>",
     "comments": [{ "path": "src/...", "line": 42, "side": "RIGHT", "body": "<코멘트>" }] }
   ```

   ```bash
   gh api repos/{owner}/{repo}/pulls/<번호>/reviews --method POST --input <파일>
   ```

5. 422 오류(줄이 diff 밖 등)가 나면 `comments`를 비우고 그 지적을 본문으로 옮겨 다시 올린 뒤 그 사실을 알린다.
6. 콘솔에는 머리줄과 올린 리뷰의 URL(`html_url`)만 적는다.

### 파일에 적으라는 지시가 있을 때

하네스 phase-review처럼 결과를 파일에 적으라고 하면 PR에 올리지 않고 콘솔 형식을 그 파일에 적는다.
